# 시작하기

백엔드 팀원이 **처음 하루 동안** 따라 하는 안내입니다. 설치부터 첫 이슈를 끝내 PR을 올리기까지 순서대로 적었습니다.

- 명령 옆의 **맥**/**윈도우** 표시를 보고 자기 컴퓨터에 맞는 것만 실행합니다. 윈도우는 PowerShell 기준입니다.
- 설치 명령은 쓰는 시점에 각 도구의 공식 안내로 한 번 더 확인하세요.

## 1. 설치할 것

| 도구 | 왜 필요한가 | 맥 | 윈도우 | 설치 확인 |
|---|---|---|---|---|
| Git | 코드 받기·올리기 | `xcode-select --install` 또는 `brew install git` | `winget install Git.Git` | `git --version` |
| GitHub CLI | 이슈·PR을 터미널에서 보기 | `brew install gh` | `winget install GitHub.cli` | `gh --version` 후 `gh auth login` |
| JDK 21 | IntelliJ에서 서버 실행(Java 21) | `brew install --cask temurin@21` | `winget install EclipseAdoptium.Temurin.21.JDK` | `java -version` → `21.x` |
| IntelliJ IDEA | 코드 편집·실행 | `brew install --cask intellij-idea` | `winget install JetBrains.IntelliJIDEA.Ultimate` | 실행되면 됨. 라이선스는 [JetBrains 교육용](https://www.jetbrains.com/community/education/)에 학교 메일로 신청(무료) |
| Docker Desktop | 개발용 DB(MySQL 9.7)와 시험용 DB | `brew install --cask docker` | `winget install Docker.DockerDesktop` | 앱을 켠 뒤 `docker version` |

- **윈도우:** 설치가 끝나면 PowerShell을 껐다 켜야 `git`, `gh`, `java` 명령이 잡힙니다.
- **Gradle은 따로 설치하지 않습니다.** 레포의 Gradle Wrapper(`./gradlew`)가 맞는 버전을 받습니다. 컴퓨터에 JDK 21이 없으면 Wrapper가 Java 21도 받아서 씁니다(터미널 실행 기준).
- **MySQL은 Docker로 모두 같은 버전(9.7)을 씁니다.** 6절의 명령 한 줄로 켜집니다. 컴퓨터에 MySQL을 직접 설치해 써도 되지만 버전은 9.7로 맞추고 `.env`의 `DB_URL`만 바꿉니다.
- **시험(`./gradlew test`)도 Docker가 켜져 있어야 합니다.** 시험은 개인 DB 대신 잠깐 쓰고 지우는 MySQL 9.7 컨테이너를 따로 띄웁니다(Testcontainers).

## 2. 레포 받기

```bash
# 원하는 폴더에서 (맥·윈도우 같음)

git clone https://github.com/Hansung-SmartRent/SmartRent-Server.git
cd SmartRent-Server
git checkout dev
```

- 기본으로 일하는 브랜치는 `dev`입니다. `main`은 발표·배포용이라 직접 올리지 않습니다.
- 폴더 이름이나 경로에 한글·공백이 없으면 Gradle 문제가 적습니다(윈도우에서 특히).

## 3. git 작성자 설정

커밋에 누가 했는지가 남습니다. **GitHub 계정의 이메일**과 같게 설정해야 GitHub에서 본인 커밋으로 보입니다.

```bash
git config --global user.name "본인 이름"
git config --global user.email "GitHub에 등록한 이메일"
git config --global user.name   # 확인
```

- 이메일을 공개하고 싶지 않으면 GitHub 설정 → Emails의 `...@users.noreply.github.com` 주소를 씁니다.
- **윈도우만:** 줄바꿈 차이로 모든 줄이 바뀐 것처럼 보이지 않게 `git config --global core.autocrlf true`를 한 번 실행합니다.

## 5. 환경변수 파일(.env) 만들기

```bash
cp .env.example .env        # 맥
copy .env.example .env      # 윈도우
```

- `.env`는 레포에 올라가지 않습니다([9절](#9-비밀정보와-올리면-안-되는-파일)).
- **DB 항목과 아래 JWT_SECRET을 채웁니다.** 메일·푸시·AI·공휴일·S3는 `..._ENABLED=false`, `STORAGE_MODE=local`로 두면 외부 서비스 없이 서버가 켜지도록 만듭니다([외부 연결](외부연결.md)의 "개발용 대체").
- `JWT_SECRET`에는 아무 긴 문자열(32자 이상)을 넣습니다. 맥은 `openssl rand -base64 48`로 만들 수 있습니다.
- 칸마다의 뜻은 [.env.example](../.env.example)에 적혀 있습니다.

### 서버가 .env를 읽는 방식

서버는 프로젝트 루트의 `.env`를 읽습니다(`application.yml`의 `spring.config.import: "optional:file:.env[.properties]"`). IntelliJ 환경변수 창에 같은 값을 다시 입력하지 않습니다.

- **프로젝트 루트에서 실행합니다.** `.env`는 실행 작업 폴더에서 찾습니다. `./gradlew bootRun`은 작업 폴더가 프로젝트 루트로 고정되어 있고, IntelliJ는 실행 설정의 **Working directory**가 프로젝트 루트인지 확인합니다.
- `.env`는 Java properties 형식입니다. `이름=값`으로 적고 따옴표나 `export`를 붙이지 않습니다. Windows 파일 경로는 `/`를 사용하면 편합니다.
- `docker compose`도 같은 `.env`를 읽어 DB 계정 이름·비밀번호를 맞춥니다.
- `.env`가 없으면 OS 환경변수에서 읽습니다. 같은 이름이 둘 다 있으면 OS 환경변수가 이기므로, 이전 IntelliJ 설정에 같은 값을 중복으로 남기지 않습니다.
- `DB_URL`·`DB_USERNAME`·`DB_PASSWORD`가 비어 있으면 서버가 켜지지 않고 `필수 설정이 비어 있습니다: DB_PASSWORD`처럼 빠진 이름을 알려 줍니다. 값은 출력하지 않습니다.
- 값을 바꾸면 서버를 다시 켭니다.
- 시험은 이 파일을 읽지 않습니다(`src/test/resources/application.yml`이 대신 쓰임). 개인 DB·외부 서비스에 연결되지 않습니다.
- EC2는 OS 환경변수로 값을 줄 수 있습니다. `.env`를 쓰면 서비스의 작업 폴더에 둡니다.

근거: [Spring Boot 외부 설정](https://docs.spring.io/spring-boot/reference/features/external-config.html)

## 6. DB와 서버 실행

프로젝트 루트에서 실행합니다. Docker Desktop을 먼저 켭니다.

```bash
# 1) DB 켜기 (처음 한 번 이미지를 받느라 조금 걸림, 다음부터는 바로)
docker compose up -d mysql

# 2) 서버 켜기
./gradlew bootRun           # 맥
.\gradlew.bat bootRun       # 윈도우

# 3) 시험 돌리기 (Docker가 켜져 있어야 함)
./gradlew test              # 맥
.\gradlew.bat test          # 윈도우

# DB 끄기 (데이터는 남음)
docker compose stop mysql
```

- 켜졌는지 확인: 브라우저에서 http://localhost:8080/api/v1/health 가 `{"success":true,...}`를 보이고, http://localhost:8080/swagger-ui/index.html 에 API 목록이 보이면 됩니다.
- **3306 포트를 이미 쓰고 있다는 오류**(`port is already allocated`, `address already in use`): 컴퓨터에 직접 설치한 MySQL이 켜져 있는 것입니다. `.env`에서 `DB_HOST_PORT=3307`로 바꾸고 `DB_URL`의 `localhost:3306`도 `localhost:3307`로 바꾼 뒤 1)부터 다시 합니다.
- IntelliJ: `SmartrentApplication`의 실행 버튼으로 켭니다. Project SDK와 Gradle JVM을 21로 맞추고, 실행 설정의 Working directory를 프로젝트 루트로 둡니다.
- 개발 설정(`SPRING_PROFILES_ACTIVE=local`)으로 처음 켜면 [fixtures](../fixtures/README.md)의 기자재·가짜 계정·공휴일이 빈 표에 들어갑니다(B1-03). 가짜 계정 비밀번호는 `demo1234`.
- `./gradlew: Permission denied`(맥)가 나오면 `chmod +x gradlew`.

## 7. 이슈 하나 끝내기

| 단계 | 할 일 |
|---|---|
| 1. 이슈 고르기 | [이슈 목록](issues/README.md)에서 "선행"이 끝난 내 이슈를 고르고 GitHub 이슈에서 담당자를 본인으로 |
| 2. 브랜치 | `git checkout dev && git pull` 후 `git checkout -b feat/#7/rental-entity` (7은 그 이슈의 GitHub 번호) |
| 3. 계획 | 이슈와 "참고 명세"를 모두 읽고, 만들 파일·표·API·시험할 사례를 정리. 문서에서 모호한 곳은 시작 전에 팀에 묻기 |
| 4. 구현·시험 | 이슈 범위만 구현, "서버 구현 후 확인할 것" 표 행마다 시험 작성, `./gradlew test` 실행 |
| 5. 확인 | 시험 결과를 보고, Swagger에서 API를 한 번 불러 보기 |
| 6. 커밋 | `feat: 대여 엔티티와 대수 계산 (#7)` 형식 |
| 7. PR | `git push -u origin 브랜치이름` 후 GitHub에서 `dev`로 PR. [PR 양식](../.github/pull_request_template.md)을 채움 |
| 8. 검토 | 다른 팀원이 아래 8절 기준으로 확인하고 승인 |
| 9. 머지 | 승인 1개 이상 + 시험 통과 후 PR 올린 사람이 머지 |

- 문서에 없는 규칙이 필요하면 임의로 정하지 말고 팀에 묻습니다. 급해서 추천값으로 만들었으면 PR 본문 "확정 안 된 것"에 적고, 팀 결정이 필요하면 [C-03](issues/C-03.md)에 추가합니다.

## 8. 브랜치·커밋·PR 규칙

- 브랜치·커밋 이름은 [CONVENTION 4절](CONVENTION.md#4-git-규칙)과 같습니다. 번호는 **GitHub 이슈 번호**를 씁니다.
  - 브랜치: `feat/#12/reservation`
  - 커밋: `feat: 예약하기 API (#12)`
  - GitHub 이슈 제목: `[FEAT] B2-03 예약하기` (종류 + 문서 번호)
- 커밋과 PR에 `#12`를 적으면 GitHub가 이슈 화면에 그 커밋과 PR을 자동으로 보여 줍니다.
- **PR 하나 = 이슈 하나.** 이슈가 너무 크면 이슈를 나눠 달라고 말합니다(PR을 크게 만들지 않기).
- PR 제목은 이슈 제목과 같게 `[FEAT] B2-03 예약하기`, 본문에 `Closes #12`. API 명세를 바꾸면 앞에 `[API]`를 붙입니다.
- 이슈를 새로 만들 때는 GitHub의 템플릿(feat, fix, docs, refactor, test, chore) 중 하나를 고릅니다. 라벨이 자동으로 붙고, 담당자 계정 라벨과 Assignees는 직접 지정합니다.
- 머지는 **Squash and merge**를 추천합니다(dev 기록이 이슈 단위로 깔끔해짐).
- **검토하는 사람이 볼 것**
  1. 이슈의 완료 조건이 다 체크됐고, 시험이 사례 ID를 덮는가
  2. 명세(openapi.yaml)의 주소·칸 이름·오류 코드와 같은가
  3. 내 담당 코드를 말없이 바꾸지 않았는가
  4. 비밀값·실제 개인 정보가 없는가
  5. 이해가 안 되는 코드가 있으면 질문(올린 사람은 모든 코드를 설명할 수 있어야 함)
- `main`으로의 머지는 발표·배포 전에 둘이 함께 합니다.

## 9. 비밀정보와 올리면 안 되는 파일

이 레포는 **공개 레포**입니다. 한 번 올라간 비밀값은 커밋을 지워도 기록에 남으므로, 올리기 전에 막는 것이 전부입니다.

| 올리면 안 되는 것 | 어디에 두나 |
|---|---|
| `.env`(DB 비밀번호, JWT 비밀키, 메일 앱 비밀번호, API 키) | 각자 컴퓨터, EC2 서버 |
| FCM 서비스 계정 키(`*.json`), AWS 키, `.pem` 접속 키 | 레포 밖 폴더(예: `~/smartrent-secrets/`) |
| 실제 학생 이름·학번·이메일·학생증 사진, DB 덤프 | 레포에 절대 넣지 않음. 시험은 fixtures의 가짜 데이터로 |
| 제조사·쇼핑몰 제품 사진 | 레포에 넣지 않음. 모델 사진은 S3(B1-08) |

- [.gitignore](../.gitignore)가 위 파일 대부분을 막지만, 이름이 다르면 못 막습니다. **커밋 전에 `git status`와 `git diff --staged`로 올라갈 파일을 직접 봅니다.**
- 비밀값을 팀원에게 줄 때는 공개 채널이 아니라 1:1로 줍니다. 메일 앱 비밀번호, API 키는 가능하면 각자 발급합니다.
- **실수로 올렸다면:** 바로 팀에 알리고 그 키를 **폐기하고 새로 발급**합니다(Google 앱 비밀번호 삭제, Google AI Studio에서 Gemini API 키 삭제, AWS 키 비활성화). 기록에서 지우는 것만으로는 안전하지 않습니다.
- fixtures의 가짜 계정 이메일로 실제 메일을 보내지 않습니다. 메일 시험은 본인 학교 메일로 합니다.

## 10. 막혔을 때

30분 넘게 막히면 혼자 붙잡지 말고 팀 채팅에 아래를 적어 묻습니다.

1. 이슈 번호와 하려던 일
2. 실행한 명령과 **오류 메시지 전체**(캡처보다 글자로 복사)
3. 이미 해 본 것
4. 운영체제(맥/윈도우)와 `java -version` 결과

자주 막히는 곳:
- **`java -version`이 21이 아님** → 여러 JDK가 깔려 있으면 IntelliJ의 Project SDK와 Gradle JVM을 21로 맞춥니다.
- **DB 연결 실패** → `docker ps`로 `smartrent-mysql`이 켜져 있는지, `.env`의 `DB_URL`·계정이 맞는지, 3306 포트를 다른 MySQL이 쓰고 있지 않은지(6절).
- **시험이 `Could not find a valid Docker environment`로 실패** → Docker Desktop을 켭니다.
- **시간이 9시간 어긋남** → 서버·DB 시간대가 `Asia/Seoul`인지, 코드에서 `Clock`을 쓰는지([CONVENTION 2절](CONVENTION.md#2-개발-규칙)).
- **문서끼리 말이 다름** → [CONVENTION 1절](CONVENTION.md#1-무엇이-기준인가-충돌하면-위가-이김)의 순서대로 따르고, 틀린 문서를 고치는 PR을 따로 올립니다.

| 할 일 | 맥 | 윈도우(PowerShell) |

## 확인 결과를 구분해서 남기기

- 서버 업무 규칙·권한·요청/응답·오류: JUnit 시험과 결과를 남깁니다.
- 메일·휴대폰 푸시·Gemini·S3·공휴일 실제 연결, EC2 재부팅·백업 복원: 해당 환경에서 실행한 시각, 조건, 성공·실패를 기록합니다. 전부 JUnit으로 대신할 수 있다는 뜻이 아닙니다.
- 운영 DB는 B1-02에서 확정할 스키마 생성 절차를 먼저 적용하고 validate로 시작합니다. 그 절차가 구현되기 전에는 운영 실행 준비가 완료된 것이 아닙니다.
- `.env` 작성만으로 환경변수가 적용됐다고 가정하지 않습니다. 5절의 로딩 방식과 6절의 실행 명령을 사용합니다.
