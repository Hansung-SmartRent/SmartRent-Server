# [FEAT] B1-18 관리자: 기기 추가·상태 변경·삭제

## 목적

기기를 늘리거나 고장 난 기기를 빼면 예약 가능 대수가 바뀝니다.

## 참고 명세

- [기획안 2장 기자재와 기기](../design/기획안.md)
- [DB 설계 3절 equipment_units, 4절 기기 삭제](../db/README.md)
- 확인 사례: `UNIT-01` 기기가 점검 중이 되어 대수가 모자라면, 신청 시각이 늦은 예약만 바로 취소하고 먼저 신청한 예약은 유지한다(학생 신고와 관리자 변경 모두) ([fixtures/cases.json](../../fixtures/cases.json))

## 만들 API

| 방법 | 주소 | 하는 일 | 권한 |
|---|---|---|---|
| POST | `/api/v1/admin/models/{id}/units` | 기기 추가 | 관리자 |
| PATCH | `/api/v1/admin/units/{id}` | 기기 이름·상태 변경 | 관리자 |
| DELETE | `/api/v1/admin/units/{id}` | 기기 삭제 | 관리자 |

요청·응답 칸과 오류 코드는 [openapi.yaml](../api/openapi.yaml)의 같은 주소를 봅니다.

## 범위

- 기기 추가(코드 중복 거절), 이름·상태(`NORMAL`/`INSPECTION`/`DAMAGED`) 변경.
- 삭제: 대여 중이면 거절, `deleted_at` 표시. 대수가 모자라게 된 예약은 [B2-16](B2-16.md) 서비스로 늦게 예약한 순서대로 경고 없이 취소.
- 상태를 점검 중·파손으로 바꿔 대수가 모자라는 경우도 같은 서비스로 같은 규칙(학생 신고와 같음, 기획안 2장).

## 연결 작업과 확인 책임

- **백엔드 1(이 이슈):** 기기 삭제·상태 변경 API를 만들고, 저장한 뒤 같은 트랜잭션에서 백엔드 2의 `OperationChangeService`(B2-16)를 호출해 돌려받은 취소·연장 목록을 응답에 넣습니다.
- **백엔드 2:** [B2-16](B2-16.md)에서 서비스와 서비스 단위 시험을 먼저 머지합니다. 이 이슈 PR의 검토자로 들어가 예약 정리 결과가 규칙대로인지 확인합니다.
- **확인 책임:** API를 불렀을 때 사례 결과가 맞는지 확인하는 API 수준 시험은 백엔드 1이 이 이슈에서 씁니다. 예약 정리 규칙 자체의 시험은 백엔드 2가 [B2-16](B2-16.md)에서 씁니다.
- [B2-16](B2-16.md)이 아직 머지 전이면 서비스 이름과 인자만 둘이 먼저 정하고, 이 이슈는 호출 부분을 빼고 진행한 뒤 [B2-16](B2-16.md) 머지 후 붙입니다.

## 완료 조건

- [ ] 기기를 지워 대수가 모자라면 가장 늦게 예약한 예약이 취소된다
- [ ] 대여 중인 기기는 삭제 불가
- [ ] 아래 표의 서버 로직·권한·응답·오류는 JUnit 시험으로 확인한다. 실제 메일·푸시·외부 API 연결, OS 명령, 배포·재부팅·백업 복원은 실제 환경 확인으로 구분해 결과를 남긴다. 시험 이름 또는 확인 기록에 이슈 번호와 행 번호·사례 ID를 적는다. 실제 연결을 가짜 응답 시험으로 대체해 완료 처리하지 않는다.
