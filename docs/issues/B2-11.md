## 만들 API

| 방법 | 주소 | 하는 일 | 권한 |
|---|---|---|---|
| POST | `/api/v1/admin/rentals/{id}/damage-discovered` | 반납 후 파손 발견 | 관리자 |
| POST | `/api/v1/admin/rentals/{id}/correct-no-show` | 노쇼 정정 | 관리자 |

요청·응답 칸과 오류 코드는 [openapi.yaml](../api/openapi.yaml)의 같은 주소를 봅니다.

## 범위

- 기기를 `DAMAGED`로 바꾸는 처리에도 [B2-16](B2-16.md)의 예약 정리 서비스를 같은 트랜잭션에서 호출합니다. 이미 점검 중으로 빠진 기기를 파손으로 바꿀 때는 수량을 이중 차감하지 않고 현재 상태로 다시 계산합니다. 연결 시험은 이 이슈 담당 백엔드 2가 맡습니다.

- 노쇼 정정: 실제 수령 시각(과거, 예약 끝 전) 입력 → `RENTING`, 그 노쇼 경고만 취소, 3회 미만이면 정지 해제, 함께 취소된 칸은 안 되살림.
- 반납 시각 정정: 연체 경고 재계산(기한 안이면 취소, 다시 늦으면 되살림), 반납으로 시작된 정지 기간 다시 계산.
- 반납 후 파손 발견: 반납된 대여에 파손 경고(학생 신고가 없었을 때), 기기 상태 변경.
- 모두 관리 기록(전·후 값).

## 서버 구현 후 확인할 것

서버를 만든 뒤 아래 입력을 넣었을 때 예상 결과가 나와야 합니다. 사례 ID가 적힌 행은 [fixtures/cases.json](../../fixtures/cases.json)에 정확한 입력과 결과가 있습니다. 시각 의존 서버 시험은 `Clock`으로 고정합니다. 실제 환경 확인은 실행 시각·환경·결과를 기록합니다.

| # | 입력·상황 | 예상 결과 |
|---|---|---|
| 1 | `NO_SHOW` 예약을 실제 수령 10:05로 노쇼 정정 | `RENTING`, 그 노쇼 경고만 취소, 같은 신청의 취소된 칸은 그대로, 관리 기록(전·후) |
| 2 | 수령 시각을 지금보다 뒤로 입력 | 400 `VALIDATION_ERROR` |
| 3 | 12:05에 반납(기한 12:00, `LATE` 1)을 11:55로 반납 시각 정정 | 그 `LATE` 경고 취소 |
| 4 | 다시 12:10으로 정정 | `LATE` 경고 되살아남 |
| 5 | 학생 신고가 없던 반납 대여에 파손 발견 | `DAMAGE` 경고 1, 기기 `DAMAGED` |
| 6 | 학생이 신고했던 반납 대여에 파손 발견 | 경고 없음 |
| 7 | 정상 기기 2대 모델에 같은 미래 시간 예약 A·B, B가 늦게 신청. 기기 1대를 파손으로 처리 | B만 즉시 취소·취소 알림, A 유지, 취소로 인한 경고 없음. 이미 점검 중인 기기의 파손 전환은 추가 수량 감소로 세지 않음 |
