## 목적

대여 중에 학생이 먼저 신고한 파손은 경고를 주지 않기 위해 기록합니다.

## 참고 명세

- [기획안 6장 반납과 연장](../design/기획안.md)
- [기획안 7장 경고와 정지](../design/기획안.md)
- [openapi.yaml](../api/openapi.yaml) `/rentals/{id}/damage-report`
- 확인 사례: `RET-02` 대여 중 스스로 신고한 파손은 경고 없음, 신고 없이 파손 반납이면 경고 1회, `UNIT-01` 기기가 점검 중이 되어 대수가 모자라면, 신청 시각이 늦은 예약만 바로 취소하고 먼저 신청한 예약은 유지한다(학생 신고와 관리자 변경 모두) ([fixtures/cases.json](../../fixtures/cases.json))

## 만들 API

| 방법 | 주소 | 하는 일 | 권한 |
|---|---|---|---|
| POST | `/api/v1/rentals/{id}/damage-report` | 기기 이상 신고 | 학생 |

요청·응답 칸과 오류 코드는 [openapi.yaml](../api/openapi.yaml)의 같은 주소를 봅니다.

## 범위

- 본인의 `RENTING` 대여에만 신고 가능. 대여 기록에 신고 표시(`broken_reported` 등 DB 설계의 칸).
- 신고한 기기는 바로 `INSPECTION`, 대여는 `RENTING` 그대로. 관리자 상태 변경과 같이 [B2-16](B2-16.md) 서비스를 불러 대수를 다시 세고, 다른 정상 기기로 줄 수 없는 예약만 늦게 예약한 순서로 취소(기획안 2장, DB 설계 4절).
- 관리자에게 `DAMAGE` 알림(B2-13 서비스 호출).
- 반납 때 이 표시를 보고 파손 경고를 빼는 것은 [B2-08](B2-08.md).

## 연결 작업과 확인 책임

- **백엔드 1(이 이슈):** 기기 이상 신고 API를 만들고, 저장한 뒤 같은 트랜잭션에서 백엔드 2의 `OperationChangeService`(B2-16)를 호출해 돌려받은 예약 정리 결과는 서버 내부 처리와 해당 예약자 알림에만 사용합니다. 학생 응답은 신고자 자신의 Rental 하나이며, 다른 학생의 이름·예약 id·취소 목록을 넣지 않습니다.
- **백엔드 2:** [B2-16](B2-16.md)에서 서비스와 서비스 단위 시험을 먼저 머지합니다. 이 이슈 PR의 검토자로 들어가 예약 정리 결과가 규칙대로인지 확인합니다.
- **확인 책임:** API를 불렀을 때 사례 결과가 맞는지 확인하는 API 수준 시험은 백엔드 1이 이 이슈에서 씁니다. 예약 정리 규칙 자체의 시험은 백엔드 2가 [B2-16](B2-16.md)에서 씁니다.
- [B2-16](B2-16.md)이 아직 머지 전이면 서비스 이름과 인자만 둘이 먼저 정하고, 이 이슈는 호출 부분을 빼고 진행한 뒤 [B2-16](B2-16.md) 머지 후 붙입니다.

- [ ] 아래 표의 서버 로직·권한·응답·오류는 JUnit 시험으로 확인한다. 실제 메일·푸시·외부 API 연결, OS 명령, 배포·재부팅·백업 복원은 실제 환경 확인으로 구분해 결과를 남긴다. 시험 이름 또는 확인 기록에 이슈 번호와 행 번호·사례 ID를 적는다. 실제 연결을 가짜 응답 시험으로 대체해 완료 처리하지 않는다.
