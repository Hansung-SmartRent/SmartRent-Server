## 목적

앱(프론트)이 실제로 부를 주소와 칸 이름을 서버 구현 전에 맞춥니다. 구현 뒤에 바꾸면 양쪽을 다 고쳐야 합니다.

## 참고 명세

## 범위

- 프론트 담당과 [openapi.yaml](../api/openapi.yaml)을 [Swagger Editor](https://editor.swagger.io)에 띄워 화면별로 필요한 API가 다 있는지 봅니다.
- 화면마다 필요한 칸이 응답에 있는지, 앱이 쓰는 이름과 다른지 확인합니다.
- 오류 코드마다 앱이 보여 줄 문구가 있는지 확인합니다.
- 바꿀 것이 있으면 [API 명세 4절](../api/README.md) 절차대로 openapi.yaml과 API README를 함께 고칩니다.
- 아래 "앱에서 고칠 것"을 프론트 담당에게 전달하고, 서버를 붙일 때 함께 고치기로 합니다.

## 앱에서 고칠 것

- 예약 시작에 내줄 정상 기기가 없으면 즉시 경고 없이 취소합니다. 서버에는 기기 반납 대기 상태·30분 수령 유예·기기 도착 알림이 없습니다. 기존 앱의 대기 표시·관련 알림·처리 로직을 서버 연결 때 제거합니다. 이번 문서 작업에서 앱 코드는 수정하지 않습니다.

1. 이미 시작한 시간 칸을 보여 주고 예약도 받음 → 기획안 3장은 예약 불가. 서버는 시작한 칸을 주지 않고 `OUT_OF_BOOKING_WINDOW`로 거절
2. 연체 경고 종류를 `OVERDUE`로 씀 → 서버·DB·API는 `LATE`
3. 노쇼를 시작 시각과 예약한 시각 중 늦은 쪽부터 셈 → 기획안은 예약 시작 시각 + 10분(시작한 칸을 막으면 두 기준이 같아짐)
4. 경고 시각을 판정이 돈 시각으로 기록함 → 서버는 마감 시각(예: 10:10:00)으로 기록(DB 설계 7절)
5. 기자재 설정: 앱 데이터는 VR 기기 5종(5·6·7·9·12번)이 반출 가능, 포터블 모니터(15번)가 당일 대여, 레이저 커팅기(29번)는 시간 제한 없음 → 학교 사이트 원문대로 VR 기기는 반출 불가, 포터블 모니터는 시작일부터 최대 7일, 레이저 커팅기는 한 번 최대 2시간

사진 인식이 끝나면 서버가 돌려준 모델의 상세 화면으로 이동하고, 없으면 찾지 못했다는 안내(기획안 10장)도 앱 화면 흐름과 맞는지 확인합니다.

- 이번에 보완한 연결 항목: 장기 예약은 pickupDate 요청, 대여 응답의 신고 내용·반납 판정·파손 처리 시각, 경고 취소 사유, 기자재 출처, 관리자 경고/정지 필터, 날짜별 관리 기록, 알림 대상 종류. 프론트의 해당 화면과 하나씩 맞춥니다.
- 통계는 API README의 추천 집계 기준을 C-03에서 확인한 뒤 기간 입력과 counts/topModels를 연결합니다.
