# 개발 규칙

백엔드 팀원이 코드를 쓰고 올릴 때 지키는 규칙입니다. 처음 준비는 [시작하기](시작하기.md), 무엇을 만드는지는 [기획안](design/기획안.md)을 봅니다.

## 1. 무엇이 기준인가 (충돌하면 위가 이김)

| 순서 | 문서 | 무엇의 기준 |
|---|---|---|
| 1 | [기획안](design/기획안.md) | 기능과 운영 규칙, 개발 범위(12장에 적힌 것만 제외) |
| 2 | [DB 설계](db/README.md) | 표와 칸, **대여 상태 전이(7절)**, 계산 규칙(6절), 판정 작업 |
| 3 | [openapi.yaml](api/openapi.yaml) | API 주소, 요청·응답 칸, 자료형, 오류 코드 |
| 4 | [API 명세](api/README.md) | 공통 규칙(날짜, 오류, 권한, 잠금), 담당, 업무 규칙 |
| 5 | [fixtures/cases.json](../fixtures/cases.json) | 규칙이 맞는지 확인하는 사례(고정 시각, 입력, 예상 결과) |
| 참고 | 앱 레포의 화면 코드 | 화면에 필요한 요청·응답·기능을 파악하는 읽기 전용 참고 자료. 앱 안의 임시 처리 결과를 서버 명세나 시험 정답의 근거로 삼지 않음 |

- 외부 서비스(메일, FCM, Gemini API, 공휴일, S3) 연결은 [외부 연결](외부연결.md).
- 할 일은 [이슈](issues/README.md) 파일 하나가 작업 하나입니다.
- 문서끼리 말이 다르면 위 순서대로 따르고, 틀린 문서를 고치는 PR을 따로 올립니다.

## 2. 개발 규칙

**규칙을 지어내지 않습니다**
- 문서에 없는 업무 규칙은 임의로 구현하지 않습니다. 그 부분은 보류하고 팀에 묻습니다. 독립적으로 진행할 수 있는 부분은 계속합니다.
- 문서의 "추천" 값은 확정 규칙이 아닙니다. 구현에 필요한 추천값은 팀과 정하고 그 문서에 결정을 반영한 뒤 씁니다(이슈 C-03). 내부 함수·변수 구성까지 따로 정할 필요는 없습니다.
- **기획안과 앱에 있는 기능은 모두 구현 범위입니다.** 기획안 12장에 적힌 기능만 만들지 않습니다.
- 명세(openapi.yaml, 문서)와 다르게 만들어야 할 것 같으면 코드를 바꾸기 전에 팀에 알립니다. 명세 변경은 [API 명세 4절](api/README.md#4-명세를-바꾸는-절차) 절차를 따릅니다.

**범위를 넘지 않습니다**
- 담당이 다른 도메인의 코드는 고치지 않습니다(아래 3절 담당표). 필요하면 담당자에게 요청합니다.
- 공용 코드(`global/`, 공통 엔티티, `build.gradle`, 설정 파일)를 바꾸면 PR 본문에 따로 적습니다.
- 관련 없는 파일의 정리, 이름 바꾸기, 형식 맞추기를 같은 PR에 섞지 않습니다.

**비밀정보를 다루지 않습니다**
- `.env`, API 키, 비밀번호, FCM 키 파일, 실제 학생 이름·학번·이메일을 코드·시험·로그·커밋에 넣지 않습니다. 설정은 환경변수로 읽고, 새 환경변수는 [.env.example](../.env.example)에 이름과 설명만 추가합니다.
- 시험 데이터는 [fixtures](../fixtures/README.md)의 가짜 데이터만 씁니다. fixtures의 이메일 주소로 실제 메일을 보내지 않습니다.

**시간은 한국 시각, 지금은 주입합니다**
- 서버·DB 시간대는 `Asia/Seoul`, DB에는 `DATETIME`(한국 시각), API는 `2026-10-07T10:00:00+09:00`.
- `LocalDateTime.now()`를 직접 부르지 않습니다. `java.time.Clock` 빈을 주입받아 `LocalDateTime.now(clock)`을 쓰고, 시험에서는 `Clock.fixed(...)`로 사례의 `given.now`를 넣습니다.

**동시 요청**
- 예약, 수령, 현장 대여, 연장은 모델 행을 `SELECT ... FOR UPDATE`(JPA `@Lock(PESSIMISTIC_WRITE)`)로 잠근 뒤 대수를 다시 셉니다([DB 6절](db/README.md#동시-요청)). 시간 칸을 미리 붙잡아 두지 않습니다.
- 신고·기기 변경·파손 반납 등 수량 변경과 예약 정리에도 같은 모델 잠금을 적용합니다.

**표 바꾸기**
- 표·칸은 엔티티만 고쳐서 바꾸지 않습니다. `src/main/resources/db/migration`에 다음 번호 SQL 파일(`V2__설명.sql` …)을 새로 만들고, 엔티티를 그 표에 맞춥니다. 이미 적용된 SQL 파일은 고치지 않습니다([시작하기 6절](시작하기.md#6-db와-서버-실행)).

**오류와 상태 값**
- 오류 코드는 [API 명세 1-6절](api/README.md#1-6-오류-형식과-상태-코드)의 목록에 있는 것만 씁니다. 새 코드가 필요하면 명세부터 고칩니다.
- 상태 값은 문서의 대문자 이름 그대로(`RESERVED`, `RENTING`, `RETURNED`, `CANCELLED`, `NO_SHOW`)이고 `@Enumerated(EnumType.STRING)`로 저장합니다.

**시험**
- 이슈의 "서버 구현 후 확인할 것" 표 행마다 JUnit 시험을 하나 이상 만들고, 시험 이름에 이슈 번호와 행 번호 또는 사례 ID를 넣습니다(예: `RSV_03_반출기자재는_다음예약_1시간전까지`).
- 실패를 숨기거나 시험을 지워서 통과시키지 않습니다.

## 4. git 규칙

- 기본 브랜치는 `dev`, 발표·배포는 `main`. 작업 브랜치는 `dev`에서 만들고 PR로 `dev`에 합칩니다.
- 이슈 번호는 **GitHub 이슈 번호**(`#12`)를 씁니다. GitHub 이슈 제목에는 종류와 문서 번호를 함께 적습니다(예: `[FEAT] B2-03 예약하기`). 문서 번호(B2-03)는 GitHub가 알아보지 못해 커밋·PR과 자동으로 이어지지 않기 때문입니다.
- 브랜치 이름: `종류/#GitHub이슈번호/짧은-영어` (예: `feat/#12/reservation`, `fix/#31/login-lock`). 여러 이슈에 걸치면 `#12-13`. 종류는 Conventional Commits 타입: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
- 커밋 메시지: `종류: 한 일 (#GitHub이슈번호)` (예: `feat: 예약하기 API와 대수 검사 (#12)`). 한 커밋에 한 가지 일.
- PR 제목은 이슈 제목과 같게(`[FEAT] B2-03 예약하기`), 본문에 `Closes #12`를 넣어 머지하면 이슈가 닫히게 합니다. API 명세를 바꾸면 제목 앞에 `[API]`를 붙입니다.
- 라벨: 작업 종류(`✨ feat`, `🐛 fix`, `📝 docs`, `♻️ refactor`, `✅ test`, `🔧 chore`) 하나와 담당자 계정 라벨(`umckee5696`, `OSJ99071`)을 붙이고, Assignees에도 담당자를 지정합니다.
- 커밋 작성자는 본인 계정입니다. `main` 강제 push와 남의 브랜치 삭제는 하지 않습니다.

## 5. 규칙이 바뀔 때 함께 맞출 것

기획안, API 명세, 앱, 서버의 동작 규칙 중 하나가 바뀌면 **같은 PR에서** 아래를 함께 맞춥니다. 결정 사항이나 질문을 따로 모아 두는 문서는 만들지 않고, 결정은 해당 명세에 바로 적습니다.

1. [기획안](design/기획안.md)의 해당 장 — 기능 규칙의 기준본입니다. 팀이 쓰던 Word 파일은 더 고치지 않고 이 파일만 고칩니다.
2. [DB 설계](db/README.md) — 표·칸, 상태 전이(7절), 계산 규칙(6절), 삭제·보존(4절)
3. [openapi.yaml](api/openapi.yaml)과 [API 명세](api/README.md) — 주소·칸·오류 코드, 업무 규칙. 순서는 [API 명세 4절](api/README.md#4-명세를-바꾸는-절차)
4. [fixtures](../fixtures/README.md) — 확인 사례(cases.json)의 예상 결과, 예시 데이터의 값(예: 경고 종류 `LATE`)
5. [이슈](issues/README.md) — 범위와 완료 조건이 바뀐 이슈, 외부 연결이면 [외부 연결](외부연결.md)
6. 앱이 바뀌어야 하면 PR 본문 "앱에서 고칠 것"에 적고 프론트 담당에게 알립니다. 앱 코드가 기획안과 다르면 기획안을 따르고 차이를 알립니다.

- 코드값(상태, 경고 종류, 알림 종류, 오류 코드)은 DB·API·예시 데이터에서 같은 이름을 씁니다. 하나를 바꾸면 모두 바꿉니다.
- 규칙을 바꾸지 않는 코드 수정은 이 절차가 필요 없습니다.
