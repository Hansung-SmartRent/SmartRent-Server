# fixtures (처음 데이터와 확인 사례)

서버를 처음 켤 때 넣는 데이터와, 규칙이 맞게 동작하는지 확인하는 사례입니다. **실제 학생 정보는 하나도 없습니다.** 학교 대여 시스템과도 연결되지 않습니다(학교 DB에 접근할 수 없음).

| 파일 | 내용 | 언제 쓰나 |
|---|---|---|
| [equipment.json](equipment.json) | 학교 대여 사이트에서 옮긴 **실제 보유 기자재 35종(기기 122대, `source: SITE`)**과 **예시 모델 8종(기기 31대, `source: EXAMPLE`)**: 장기 대여 노트북 5종, 2일 이상 대여 휴대용 모니터 3종. 모델 정보(운영 시간, 간격, 반출 여부 등)와 기기 코드·상태 | 개발 DB를 처음 채울 때 |
| [users.json](users.json) | 가짜 계정 7개(승인, 승인 대기, 반려, 정지, 학생증 미제출, 관리자) | 로그인·권한 확인 |
| [holidays.json](holidays.json) | 2026·2027년 공휴일 40일 | 공공데이터를 받기 전, 받기에 실패했을 때 |
| [rentals.json](rentals.json) | 상태별 대여 예시 7건(예약, 대여 중, 파손 신고, 반납, 노쇼, 취소) | 앱 화면을 눈으로 확인할 때 |
| [cases.json](cases.json) | **확인 사례 26개.** 고정 시각, 입력, 기대 결과가 적혀 있어 JUnit 시험으로 그대로 옮길 수 있음 | 기능을 만들고 "완료"를 판단할 때 |

## 알아 둘 점

- **학교 사이트에서 옮긴 `guide`는 출처 원문입니다.** 앱·CSV의 설정값에 맞춰 원문을 고치지 않습니다. 예시 모델(`EXAMPLE`)의 안내는 팀의 확정 규칙에 맞춰 작성합니다.
- **원문을 따라 정한 설정:** key `5`, `6`, `7`, `9`, `12`(VR 기기)는 원문대로 반출 불가(`carryOut: false`)입니다. key `15`(포터블 모니터)는 원문 "1회 최대 일주일 간 대여 가능"대로 2일 이상 대여(`multiDay: true`)이고 `maxRentalDays: 7`입니다. 이 품목만 반납일 한도가 다음 주 금요일이 아니라 대여 시작일부터 7일입니다(기획안 4장). key `29`(레이저 커팅기)는 원문 "1인당 1대 2시간 사용"대로 `maxRentalMinutes: 120`입니다(한 신청의 칸 합계와 연장 포함, 기획안 3장). 수업 여부·필라멘트 양·관리자 입회 같은 원문 규칙은 서버가 막지 않고 안내문으로 보여 줍니다.

- **기기 코드(`units[].code`)는 기기에 붙은 QR·바코드 값입니다.** 지금은 앱에서 쓰던 번호를 그대로 옮겼습니다. 실제 바코드 값과 다르면 기자재실 목록을 받아 바꿉니다.
- **점검 중(`INSPECTION`) 기기 7대**는 학교 사이트에서 "대여 가능 0"으로 나온 품목입니다.
- **모델은 `key`로 가리킵니다.** 앱(`src/data/equipment.json`)의 모델 id와 같은 값입니다(`15`, `30`, `demo-lg`). `siteNumber`는 학교 사이트 번호라 실제 기자재(SITE)에만 있습니다. rentals.json과 cases.json도 `key`를 씁니다.
- **예시 모델 8종은 장기 대여·2일 이상 대여 기능을 보여 주려고 넣었습니다**([기획안 4장](../docs/design/기획안.md#4-장기-대여)). 실제 목록에 없다는 이유로 빼거나 하루 대여로 바꾸지 않습니다.
  - 장기 대여(`exampleFor: LONG_TERM`): 노트북 5종(key `30`~`34`: 맥북, 삼성 노트북, LG 그램, MSI 노트북, HP 노트북). 학교 사이트 원본 목록에는 없고 팀이 장기 대여 기능용으로 만든 모델이라, 장소·연락처·기기 이름·구입 연도도 예시 값입니다. 운영 09:00~17:00, 기기 5대씩.
  - 2일 이상 대여(`exampleFor: MULTI_DAY`): 휴대용 모니터 3종(key `demo-lg`, `demo-asus`, `demo-lenovo`: LG gram +view 16MR70, ASUS ZenScreen MB16AHV, Lenovo ThinkVision M14t Gen2). 앱 설정 그대로 `multiDay: true`, 반출 가능, 09:00~20:00, 1시간 간격, 기기 2대씩, 장소는 비어 있음.
- **43종 = 실제 35종 + 예시 8종**입니다. 실제 35종은 사이트 상세에서 옮긴 23종과 사이트 "기자재 전체" 목록에서 옮긴 12종(key `38`~`49`)입니다.
- **모델 사진은 이 레포에 없습니다.** `appImageId`는 앱 레포 `src/assets/equipment/{번호}.png`를 가리킵니다. 사진을 S3에 올리는 일은 이슈 B1-08에서 합니다. 일부 사진은 제조사·쇼핑몰 사진이라 공개 레포에 올리지 않습니다.
- **users.json의 비밀번호는 개발용입니다.** DB에 넣을 때 BCrypt로 바꾸고, 이 주소들로 메일을 보내지 않습니다.
- **rentals.json의 날짜는 "운영일 기준 며칠 뒤"로 적었습니다.** 넣는 순간을 기준으로 날짜를 계산해야 화면이 늘 그럴듯해 보입니다. 규칙 시험에는 날짜가 고정된 cases.json을 씁니다.

## cases.json 읽는 법

사례 하나는 이렇게 생겼습니다.

```json
{
  "id": "RSV-03",
  "title": "반출 가능 기자재는 다음 예약 1시간 전까지만 예약된다",
  "rule": "기획안 3장",
  "status": "확정",
  "api": "POST /reservations",
  "given": { "now": "2026-10-07T09:00:00+09:00", "model": { ... }, "existing": [ ... ] },
  "when": [ { "segments": [ ... ] }, { "segments": [ ... ] } ],
  "then": [ { "result": "성공", "status": "RESERVED" }, { "errorCode": "NO_CAPACITY" } ]
}
```

- `given`은 시험 전에 DB에 넣을 상태, `when`은 보낼 요청, `then`은 기대 결과입니다. `when`과 `then`이 배열이면 같은 순서끼리 짝입니다.
- 모든 시각은 한국 시각(+09:00)입니다. 시험에서는 서버의 "지금"을 `given.now`나 `when[].at`으로 고정해야 합니다. 방법: 서비스에 `java.time.Clock`을 주입받게 만들고, 시험에서 `Clock.fixed(...)`를 넣습니다.
- **예상 결과의 근거는 사례마다 `rule` 칸에 적은 기획안 장과 DB·API 명세 절입니다.** 이 파일은 직접 고칩니다. 규칙이 바뀌면 기획안·DB·API 명세를 맞춘 뒤 사례를 함께 고칩니다([CONVENTION 5절](../docs/CONVENTION.md#5-규칙이-바뀔-때-함께-맞출-것)).
- 서버 구현이 이 사례를 모두 통과해야 완료입니다. 어떤 이슈가 어떤 사례를 쓰는지는 [이슈 목록](../docs/issues/README.md#확인-사례와-이슈)에 있습니다.

## DB에 넣는 방법

처음 데이터를 넣는 코드는 이슈 **B1-03**에서 만듭니다. 추천 방식은 개발용 설정(`spring.profiles.active=local`)일 때만 서버가 켜지면서 이 JSON들을 읽어 비어 있는 표를 채우는 것입니다. 운영 서버에는 기자재와 관리자 계정만 넣고 가짜 학생·대여는 넣지 않습니다.
